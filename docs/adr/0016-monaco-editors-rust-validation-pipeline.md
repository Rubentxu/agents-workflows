## Context

Studio has 6 resource editors (Agent, Skill, Prompt, Template, Tool, Workflow) built as HTML forms with `<input>`, `<textarea>`, and `<select>` elements. These editors:

1. **Don't respect native formats** — Skills are Markdown+frontmatter but the editor uses a textarea
2. **Have no validation** — The YAML parser (`extractYamlSpec`) fails on backend YAML format, fields load empty
3. **Have no autocomplete** — No ARN completion, no field suggestions, no hover docs
4. **Are disconnected from files** — Editors work against REST DTOs in SQLite, not the actual resource files
5. **Don't support professional workflows** — Programmers expect VSCode-quality editing: syntax highlighting, errors inline, schema-driven completion

Research into industry standards reveals:

| Tool | Editor | Validation | Architecture |
|------|--------|------------|--------------|
| **OpenShift Console** | Monaco (`AsyncResourceYAMLEditor.tsx`) | Server-side API | PatternFly + Monaco |
| **GitHub Actions** | Monaco + `actions/languageservices` | JSON Schema | Schema-driven autocomplete |
| **GitLab Pipelines** | Custom React + Monaco | GitLab CI lint API | Schema + custom linters |
| **vscode-yaml** | Monaco via `monaco-yaml` | `yaml-language-server` (Red Hat) | JSON Schema + LSP |
| **Lens** | Monaco | K8s API server | Schema + server validation |

The `monaco-yaml` package (325 stars, MIT) wraps `yaml-language-server` (1.5k stars, Red Hat) for browser use. It provides: autocomplete, hover docs, schema validation, formatting, document symbols — all driven by JSON Schema.

The `schemars` crate (1.4k stars) generates JSON Schema from Rust derive macros (`#[derive(JsonSchema)]`), respecting `#[serde(...)]` attributes. This means schemas NEVER desync from code.

## Decision

We adopt a **4-layer validation architecture** with Monaco editors per resource type and Rust-powered server-side validation.

### Layer 1: Client-side (Monaco + monaco-yaml)

- Monaco Editor as the primary editing surface (target: replaces all HTML forms)
- `monaco-yaml` web worker provides YAML syntax validation and schema-driven autocomplete
- JSON Schema served from `/api/schemas/:type` endpoint (generated by `schemars`)
- Runs in browser, instant feedback on syntax errors

### Layer 2: Schema Validation (Rust serde)

- On save (`PUT /api/content/:arn`), backend parses content with `serde_yaml`
- Type checking against domain structs: field types, required fields, enums, ranges
- Structured errors with line/column numbers
- Prevents invalid data from being persisted to files

### Layer 3: Cross-reference Linter (Rust custom, implemented)

- Resolves ARN references against the registry (`crates/validation/src/arn.rs`)
- Validates: "does `prompt: arn:local:global:prompt/foo` actually exist?"
- Validates: "do the skills listed in this agent have their `required_tools` in the agent's `tools` map?"
- Returns warnings (not errors) for broken references

### Layer 4: Semantic Linters (Rust custom, implemented)

- Domain-specific rules beyond schema validation (`crates/validation/src/lib.rs:213-492`)
- Agent without prompt → warning
- Workflow DAG cycle detection → error (via orphan stage detection)
- Workflow orphan stages → warning (via `DUPLICATE_STAGE`, `UNDEFINED_DEPENDENCY`)
- Template `{{variables}}` mismatch with prompt → information (via `UNDECLARED_VARIABLE`)

|----------|--------|--------------------|

### Content API

A generic endpoint replaces per-resource DTOs for file content:

```
GET  /api/content/:arn  → raw file content (text/yaml | text/markdown)
PUT  /api/content/:arn  → write raw content → file → re-index SQLite
POST /api/validate/:arn → parse + validate, return Diagnostic[]
GET  /api/schemas/:type → JSON Schema (schemars-generated)
```

The editor reads and writes raw file content. The backend handles parsing, validation, and index updates.

### Save Flow

**End-to-end save for Monaco/frontmatter editors:**

1. **User clicks Save** in Monaco editor (single YAML) or FrontmatterEditor (YAML + MD)
2. **Frontend**: Editor content is bundled:
   - Single YAML resource (Agent, Tool, Workflow): raw YAML string
   - Frontmatter resource (Skill, Prompt, Template): `YAML header + --- + MD body` concatenated
3. **Validation gate** (optional, triggered by `POST /api/validate/:arn`):
   - Backend runs Layer 1–4 validation pipeline
   - Returns `Diagnostic[]` with line/column, severity, message
   - If errors: editor shows inline markers, save blocked
   - If warnings/info: editor shows markers, save allowed
4. **Persist** (triggered by `PUT /api/content/:arn` with `Content-Type: text/yaml` or `text/markdown`):
   - Backend writes raw content to filesystem at resolved ARN path
   - On success: re-indexes SQLite from updated files
   - On failure: returns error, SQLite unchanged
5. **Response**: Backend returns 200 OK or error with message

**Validation-on-save vs validation-on-change:**
- Debounced real-time validation via `POST /api/validate/:arn` while typing (Layer 1 syntax only)
- Full validation on explicit save attempt (all 4 layers)
- The save button is enabled always; validation errors are shown inline, not as modal dialogs

### Frontmatter Split (Skill, Prompt, Template)

Resources with Markdown+frontmatter use **two coordinated Monaco instances** that appear as a single editing surface:

```
┌──────────────────────────────────────────────┐
│ ---                                          │  ← Monaco #1: YAML mode
│ arn: arn:local:global:skill/sdd-explore      │     schema-validated frontmatter
│ name: sdd-explore                            │
│ triggers:                                    │
│   - "explore codebase"                       │
│ required_tools:                              │
│   - bash                                     │
│ ---                                          │  ← separator (rendered, not editable)
│                                              │
│ # SDD Explore Skill                          │  ← Monaco #2: Markdown mode
│                                              │     syntax highlighting
│ You are an SDD executor...                   │     {{variable}} detection
└──────────────────────────────────────────────┘
```

On save, both editors' content is concatenated with `---` separators into a single file.

### Workflow Dual Editor

Workflows have two editing modes in tabs:

- **Visual tab**: React Flow DAG (existing `WorkflowEditorPage`) — drag stages, connect dependencies, assign agents
- **Code tab**: Monaco YAML editor with workflow schema — edit raw YAML with full validation

Bidirectional sync: changes in visual update YAML model, changes in YAML update visual. Both share the same data model.

### New Crates

**`crates/schema`** — JSON Schema generation:

```rust
// Derives JsonSchema on all resource spec types
// Generates schemas for: agent, skill, prompt, template, tool, workflow
// Also generates schemas for frontmatter of: skill, prompt, template
// Served via GET /api/schemas/:type
```

**`crates/validation`** — Validation engine:

```rust
pub struct Diagnostic {
    pub line: u32,
    pub column: u32,
    pub severity: DiagnosticSeverity,  // Error | Warning | Information | Hint
    pub message: String,
    pub code: Option<String>,          // e.g. "arn-resolve-failed"
    pub source: String,                // e.g. "crossref-linter"
}
```

### Filesystem as Source of Truth

Files are the source of truth. SQLite is a cache/index. This follows the Kubernetes pattern:

- **Read flow**: File → parse → index in SQLite → serve via REST
- **Write flow**: REST → validate → write file → re-index SQLite
- **On startup**: `register_resources_to_db()` rebuilds SQLite from files

## Consequences

### Positive
- **Professional editing experience** — VSCode-quality editors for all resource types
- **Single source of truth for schemas** — Rust types generate both server validation AND client autocomplete
- **Real-time validation** — Debounced server-side validation with structured diagnostics
- **ARN cross-reference checking** — Beyond JSON Schema: validates references against live registry
- **Files as truth** — Editable with external tools (vim, VSCode), version-controllable
- **Extensible linters** — New validation rules are Rust functions, not frontend code
- **Format-native editing** — Each resource edited in its natural format

### Negative
- **Bundle size increase** — Monaco adds ~2MB to Studio bundle
- **Web worker complexity** — `monaco-yaml` requires a web worker for yaml-language-server
- **Two new crates** — `schema` and `validation` increase maintenance surface
- **Frontmatter coordination** — Two Monaco instances need careful sync for save/load
- **Migration** — Existing form-based editors replaced entirely
